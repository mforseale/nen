# Nen — архитектура развития

По логу VM ежедневные копии установлены, первая создана и таймер активен. Следующий переход — [первое подключение рабочей БД к Alembic](vm-baseline-bootstrap.md): root-владелец отдельного набора migration tools в `/opt`, репетиция на восстановленной копии, затем короткая остановка только API и регистрация baseline со свежим snapshot. Выполнение этого перехода ещё ожидается; последующие записи сохранены как история.

Третий этап CI/CD — [миграции и резервные копии](database-migrations-and-backups.md): зафиксированная начальная ревизия Alembic, проверяемое подключение существующей SQLite, снимок перед изменением схемы и восстановление в новый файл. API требует актуальную ревизию вместо `create_all()` при запуске. Подготовлен первый установщик ежедневных копий; на VM он ещё не применялся.

Второй этап CI/CD: проверки GitHub Actions описаны в [continuous-integration.md](continuous-integration.md). Workflow `CI` проверяет API и frontend на Ubuntu 22.04 с Python 3.10 / Node 24 при push и PR в `main`; production-доступ и автоматический deploy на этом этапе не добавляются.

Первый этап CI/CD — общий репозиторий [mforseale/nen](https://github.com/mforseale/nen): [repository.md](repository.md). Выбраны корневой monorepo, ветка `main`, сохранение исходного коммита frontend и исключение локальных данных из Git. Это уточняет прежний план ниже; рабочая VM на этом этапе не меняется.

Расположение кода, данных и настроек на VM и предложение CI/CD: [ci-cd-plan.md](ci-cd-plan.md). Следующий этап — общий репозиторий, CI на Linux, готовые релизы по commit SHA и переключение через current с сохранением постоянной SQLite. Это пока план: workflow, удалённый репозиторий и deploy-доступ не созданы; текущая установка не менялась.

План размещения на одной Linux VM: [linux-deployment.md](linux-deployment.md). Подтверждены Ubuntu 22.04 x86_64 с 2 ГиБ RAM, Python 3.10, установленный Node.js 24 LTS, 4 ГиБ swap, пользователь `nen`, публичный IP и SSH. Для переноса подготовлен архив исходников без локальных настроек, зависимостей и БД; согласованная копия данных хранится отдельно. Сервисы и база остаются на VM, внешний доступ — через reverse proxy с HTTPS. Перенос, сборка, запуск и публичный DNS-домен пока не подтверждены.

Пользователь затем подтвердил перенос и сборку и выбрал пустую БД. Для первого запуска подготовлен `scripts/setup-vm-services.sh`: отдельные systemd-службы от `nen`, один API worker, постоянная SQLite вне кода, оба порта на loopback. Первое открытие — SSH-туннель к Next.js; внешний Caddy с HTTPS настраивается после проверки служб. Старые записи статуса выше сохранены как история.

Получен вывод VM: обе службы включены и работают, пустая БД создана, health напрямую и через frontend, а также HTTP-загрузка главной успешны. Это подтверждает серверный запуск; регистрация в браузере и повторный старт после перезагрузки ещё ожидают проверки. Следующий этап — Caddy и внешний доступ с учётом доступного домена/IP и занятости портов.

Публичного домена у пользователя нет. Для продолжения выбран вариант Caddy + публично доверенный HTTPS по IP с ACME shortlived; перед применением ожидаем проверку портов и firewall. SSH-туннель остаётся способом предварительного просмотра, а не обязательным способом доступа после публикации.

Проверка портов выявила существующий Xray на TCP 443. Он сохраняется; стандартное размещение Caddy на 443 пока не подходит. Рассматриваем HTTPS на отдельном 8443 и ACME HTTP-01 на 80, без вмешательства в Xray. Браузерный просмотр через SSH сначала работал, затем пропал; перед публикацией повторно проверяем health служб и состояние туннеля. Конфигурация Caddy ещё не применялась.

Повторный health VM подтвердил работоспособность API и frontend. Для публичного доступа подготовлен `scripts/setup-vm-caddy.sh`: адрес `https://144.31.189.98:8443`, ACME shortlived для IP через HTTP-01 на 80, без TLS-ALPN на занятом 443. Сначала Caddy отдаёт служебный 503, после проверки доверенного сертификата включается Secure-cookie и reverse proxy на Next.js. Xray, существующая БД и SSH-правила сохраняются. Установка и проверка с внешнего браузера ещё ожидаются.

Позднее подтверждены внешний браузерный доступ на 8443 и полный успешный лог Caddy 2.11.7, HTTPS health и Secure/HttpOnly. Пользователь запросил перенос на 443 после самостоятельного освобождения порта. Инструкция записана в linux-deployment.md: копия Caddyfile, замена глобального https_port и адреса блока, validate и reload-or-restart. Такой перенос пока планируется; рабочий подтверждённый адрес остаётся на 8443 до нового вывода пользователя. HTTP 80 остаётся для продления сертификата, внутренние порты приложения — 3000/8000.

Получен вывод выполнения переноса: свободный 443 проверен, Caddyfile изменён, validate успешен, применение через systemd прошло без выведенной ошибки. Текущий целевой публичный адрес — `https://144.31.189.98/`; health и браузерный доступ после этой смены ещё должны быть подтверждены. В дополнительной команде пользователя `caddy.se` — обрезанное имя, используется `caddy.service`.

## Решение от 18 октября 2026

Сохраняем Next.js 16 / React 19 и FastAPI / SQLAlchemy / SQLite. Фон главной `/nen-bg.jpg` и исходные изображения не заменяем. Интерфейс — чёрный, серебряный и тёмно-красный, с типографикой и свободным пространством вместо неоновых игровых панелей.

## Данные и доступ

- Системный каталог имеет стабильные идентификаторы. Common длится 7 дней, rare — календарный месяц, epic — календарный год, legendary — без конечной даты. Дата окончания вычисляется при заключении.
- Заключённый пакт — существующая сущность `Pact`. Дополнительные параметры храним в новой таблице `pact_details`, не меняя и не удаляя существующие записи.
- Совместный пакт создаётся в состоянии draft, получает запрос второму пользователю и становится active только после принятия. Условия и срок фиксируются до отправки. Отказ отменяет пакт. Доступ есть только у участников.
- Дневные отметки уникальны для сочетания пакт / пользователь / дата. Прогресс конечного пакта — доля отмеченных дней от его длительности; для пожизненного показываем количество дней. Браузер передаёт локальную дату и смещение от UTC, сервер сверяет их с текущим временем. Истечение срока проверяется по UTC-времени, а не по локальной дате, чтобы не терять последний день в Томске и других часовых поясах.
- Заметки: public, invited, private. Для invited есть явный список пользователей с доступом; проверки выполняются API. Публичный профиль и поиск не раскрывают почту и закрытые заметки.
- До 10 календарей на пользователя. Цвета уникальны внутри набора. Записи привязаны к календарю и владельцу, общий вид объединяет выбранные календари.
- Комментарии системных пактов образуют публичный форум. Комментарии совместных пактов доступны участникам. Trending считается по числу сообщений за последние 7 дней.
- Любая запись и изменение требуют действующей HTTP-only сессии. Старые незащищённые методы пактов заменяются проверками владельца/участника.

## Изображение и интерактивность

Сердце с цепями — отдельная подробная растровая иллюстрация без нарисованных кинжалов. Кинжалы — индивидуальные SVG-объекты со стабильным `data-pact-id`, построенные только из активных пактов API. В сцене до 8 кинжалов одновременно, остальные доступны постранично; число отображённых совпадает с выбранной страницей активных пактов. Это сохраняет читаемость при любом количестве пактов.

Сердце, цепи и кинжалы находятся в общей медленно пульсирующей группе. Масштаб меняется менее чем на 2%. Наведение/фокус/нажатие выделяет кинжал и открывает доступную карточку; карточка остаётся открытой при переходе курсора на неё. При reduced motion анимации отключаются. Если пактов нет, кинжалов нет.

## Проверка и запуск

API тестируется на отдельной временной SQLite: сессии, приглашения, ежедневные отметки, приватность заметок, лимит календарей и доступ к чужим данным. Frontend проверяется TypeScript и production build; интерактивность и адаптивность — локальным браузером при доступности. Реальные пользовательские данные при проверках не изменяются.

Изменения локальные; внешняя публикация и смена платформы не входят в эту задачу.

## Уточнения от 19 октября 2026

- Условия пакта фиксируются при заключении. Старые небезопасные URL создания и изменения возвращают подсказку использовать каталог или приглашения.
- Проверка лимита календарей и повторного заключения шаблона выполняется внутри блокировки. Ответ на совместное приглашение сохраняется атомарно только из pending; повторное принятие не создаёт ещё одного участника.
- Личные запросы идут через Next.js rewrite `/api/v1` к FastAPI на `127.0.0.1:8000`. Cookie остаётся на домене сайта; адрес API не зашит в браузер как localhost.
- При включённом cacheComponents URL-зависимые компоненты Next.js находятся внутри Suspense, в том числе навигация динамических страниц.
- Browser QA недоступна в текущей сессии: нет подключённого in-app browser или Chrome. Это не заменяется утверждением о визуальной проверке. Выполняются API-тесты, TypeScript, production build, серверный рендер сцены и HTTP-проверки.

## Оформление: уточнение от 19 октября 2026

По обратной связи пользователя убираем мотивационные цитаты и вступительный hero-блок. Главная сразу открывает каталог; названия разделов становятся прямыми и функциональными.

Исходный `nen-bg.jpg` остаётся в проекте и используется внутри main как фоновая иллюстрация каталога. Шапка находится вне области фона и имеет непрозрачную чёрную подложку. Это сохраняет фон, не накладывая изображение на навигацию.

Увеличиваем основной кегль, насыщенность и контраст текста, особенно названий пактов и подписей. Уровни получают более заметные серебристый, синий, фиолетовый и золотой акценты в метках и границах карточек. Не добавляем неоновое свечение.

В навигации текст сопровождается иконками. Поиск при фокусе показывает вертикальные строки категорий: «Пакты», «Пользователи», «Заметки». После выбора категория видна в поле, а результаты появляются ниже списка. Поиск сохраняет прежний API и проверки приватности; поддерживает клавиатуру, Escape и закрытие при выходе фокуса.
