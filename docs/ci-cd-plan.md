## Предлагаемая схема

Один общий Git-репозиторий для `api`, `web`, `scripts`, `docs` и workflow. Сохраняем одну VM, Caddy, systemd и постоянную SQLite. Сборку выполняет GitHub Actions на отдельном hosted Linux runner; VM с 2 ГиБ RAM принимает подготовленный релиз. Это разгружает production во время сборки.

```text
PR / push → CI: API-тесты + frontend-тесты + lint + production build
                                  ↓
push в основную ветку → архив конкретного commit SHA
                                  ↓ SSH
VM: подготовка релиза → backup SQLite → миграции → переключение
                                  ↓
                    restart API/web → HTTPS health
                                  ↓ ошибка
                    возврат совместимой предыдущей версии
```

Для нового общего репозитория предлагаем основную ветку `main`; это предложение, текущая `master` не переименовывалась. Deploy запускается после успешных проверок доверенного push в основную ветку. Для PR выполняются проверки без доступа к production SSH-ключу. Нормальный deploy обновляет приложение; Caddy и его сертификаты продолжают работать независимо.

## CI и содержимое релиза

На начало реализации фиксируем runner `ubuntu-22.04` x64, Python 3.10 и Node 24, согласованные с VM. По официальному списку GitHub этот runner доступен на дату документа. Явный образ снижает риск переноса нативных зависимостей, собранных под более новую glibc. В дальнейшем образ обновляется вместе с проверкой совместимости VM.

Проверки по фактическим scripts проекта:

- API: установка `api/requirements.txt`, `python -m unittest discover -s tests -v`, `python -m pip check`. База тестов изолирована от production.
- Frontend: `npm ci`, `npm test`, `npm run lint`, `npm run build`.
- При сборке `NEN_API_ORIGIN=http://127.0.0.1:8000`; публичный `NEXT_PUBLIC_API_URL` не задаётся.

Для компактного frontend-артефакта предлагаем Next.js `output: "standalone"`. Сейчас этот параметр ещё не включён. В runtime-пакет нужно добавить `public` и `.next/static`: standalone сам их не копирует. Запуск — `node server.js` с loopback hostname и портом 3000. Это потребует один раз обновить ExecStart службы frontend и проверить изображения, файлы, rewrite API и приватные маршруты на новой сборке.

Архив `nen-<commit-sha>.tar.gz` содержит подготовленный frontend, исходники API, requirements/будущие миграции и метаданные версии. Это один и тот же проверенный артефакт, который передаётся в deploy, без повторной сборки frontend на VM. Не архивировать production БД, рабочие env, SSH-ключи или Windows venv. Python venv создаётся на VM сразу в окончательном каталоге нового релиза; готовый venv с runner не переносится, его абсолютные пути могут быть неверны.

## Каталоги и переключение на VM

Планируемое расположение, которого пока нет:

```text
/srv/nen/incoming/                 входящие архивы
/srv/nen/releases/<commit-sha>/    отдельный готовый релиз
/srv/nen/current -> releases/...   выбранный релиз
/var/lib/nen/pact.db               существующие пользовательские данные
/etc/nen/api.env                  существующие настройки
/var/lib/caddy/                   существующее состояние TLS
```

Обе app-службы переводятся на пути через `current`; backend использует абсолютный путь `/var/lib/nen/pact.db`. Для frontend требуется обновить `ReadWritePaths`, потому что сейчас разрешена запись в `/srv/nen/web/.next`, а будущий runtime-кэш будет внутри выбранного релиза. Подготовка релиза и зависимостей выполняется до остановки рабочих процессов. При переключении обе app-службы перезапускаются согласованно. Ожидается короткое окно недоступности при рестарте; полное отсутствие простоя эта схема не обещает.

Первый переход со старых каталогов и `next start` на current/standalone — отдельная разовая миграция с сохранёнными исходными service-файлами и прежней установкой. Он не должен случайно уничтожить `/srv/nen/api` и `/srv/nen/web` ради освобождения места. После успешной миграции обычные релизы переключаются одной и той же процедурой.

Новый релиз получает собственную Linux venv и проверяется до переключения. Установка зависимости не должна оставлять частично обновлённую старую venv. Одновременные deploy блокируются на VM через flock и сериализуются workflow; запущенный deploy не отменяется посреди миграции ради следующего commit. Предыдущие успешные релизы сохраняются для отката в пределах выбранного лимита диска.

## Доступ из CI

Для SSH предлагается отдельная учётная запись `nen-deploy` и отдельный ключ, а не существующий root-доступ. Ключ хранится в GitHub Actions secrets, публичный host key VM фиксируется после проверки. У deploy-пользователя — каталог входящих релизов и ограниченная команда применения, без произвольного sudo.

Root-владелец серверного deploy-wrapper задаёт допустимые пути, формат commit SHA и команды управления двумя app-службами. Архивы распаковываются с проверкой путей и ссылок. Обработка исходников и установка Python-зависимостей не выполняются от root. Процессы сайта продолжают работать от `nen`; env и сертификаты остаются вне релизов.

GitHub environment `production` можно добавить для отображения истории и ограничения ветки, если это доступно на выбранном тарифе/типе репозитория. Обязательное ручное согласование не вводится этим планом. Конкретное хранение секретов выбирается по доступности GitHub-функций; обычные repository secrets достаточны для первого workflow с проверенным ограничением deploy на основную ветку.

## Миграции и возврат версии

Сейчас Alembic не готов для автоматического production deploy: `api/alembic/versions` не содержит ревизий; `env.py` берёт URL из ini, а `api/alembic.ini` содержит `sqlite:///./pact.db`. Простой запуск upgrade без изменения конфигурации не направит миграции на `/var/lib/nen/pact.db`. Текущий `Base.metadata.create_all()` не обновляет уже существующие колонки.

Перед включением автоматического CD нужно:

1. Подключить production `DATABASE_URL` к Alembic и сформировать baseline текущей схемы.
2. Проверить создание новой БД через миграции и обновление согласованной копии текущей БД. Существующая база получает baseline только после проверки соответствия схемы.
3. Настроить согласованную SQLite online backup перед миграциями и проверить восстановление отдельно от production. Загруженные файлы тоже находятся в этой БД.
4. Для обычного deploy выполнять миграции перед запуском нового кода, сохраняя совместимость с предыдущим релизом.

После рестарта проверяются API health, тот же endpoint через публичный HTTPS, главная и статические файлы; добавляется минимальная проверка входа/чтения данных тестовым пользователем без модификации чужих аккаунтов. При неуспешном старте возвращается предыдущий код, если схема БД с ним совместима. Автоматически восстанавливать старый снимок поверх живых новых данных нельзя: откат БД отдельно учитывает записи после backup. Для разрушительных миграций нужен отдельный план восстановления.

## Последовательность реализации

1. Общий репозиторий с сохранением текущей истории/изменений; исключение env, БД, кэшей и резервных копий из Git.
2. CI на PR и основной ветке, ещё без production deploy.
3. Миграции и backup/restore; подготовка и проверка standalone-пакета.
4. Разовая миграция VM на releases/current и настройка ограниченного deploy-доступа.
5. CD проверенного commit с HTTPS-проверкой, сериализацией запусков и проверенным откатом кода.

Подключение GitHub, публикация исходников, создание ключей и настройка VM ещё не выполнялись в рамках этого плана.
