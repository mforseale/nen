# Отзывчивость редакторов и добавление файлов

Решение от 20 октября 2026 после сообщения о небольших задержках при вводе и
добавлении файлов. Дополняет [посты и черновики](responsive-social-and-streaks.md)
и [поведение окон](dialogs-and-background.md); заменяет сохранение всего File[]
при каждом изменении текста и размытие фона открытого диалога.

## Причины и решение

В PostEditor каждый символ вызывал полную запись черновика в IndexedDB, включая
прикреплённые File. Маленькие миниатюры показывали исходные полноразмерные файлы.
Все диалоги дополнительно размывали фон всей страницы через backdrop-filter.
Свободные RAM/CPU на VM не исключают эти затраты в браузере.

- Текст имеет немедленный небольшой checkpoint в localStorage; основная запись
  метаданных объединяется через 450 мс после паузы ввода. При изменении файлов,
  закрытии, публикации и pagehide запись запускается сразу.
- IndexedDB повышена с версии 1 до 2: существующий `drafts` сохраняется, добавляется
  `attachments`. Метаданные и File[] обновляются одной транзакцией, байты файлов
  записываются только при изменении набора вложений. Массив файлов стабилен при
  вводе текста и повторном открытии сохранённого черновика. Сильного глобального
  кеша File, удерживающего файлы закрытых редакторов в RAM, нет.
- Старые черновики со встроенными File читаются без потерь и нормализуются при
  следующем сохранении. Более новый текстовый checkpoint сохраняется при завершении
  старой асинхронной записи; если вложения уже сохранены, он восстанавливает их
  вместе с последним текстом. Ошибка записи новых файлов удерживает редактор открытым.
- Миниатюры создаются асинхронно до 192×192; ImageBitmap закрывается, object URL
  отзывается при удалении/закрытии. Оригинальные File передаются серверу без сжатия
  и изменения байтов. Ошибка миниатюры оставляет доступный файл с иконкой.
- Редакторы сохраняют тёмную подложку; полноэкранное размытие фона убрано. Строки
  новых вложений мемоизированы, чтобы не перерисовываться при каждом символе.
- У SiteHeader убран второй обработчик focus: useApi уже обновляет запросы при
  возврате к окну. Периодический опрос уведомлений работает только в видимой вкладке.

## Проверка

В одном сценарии Chrome с десятью PNG 4096×3072 и одинаковой строкой текста
до правки было 79 put, все включали файлы; после правки при вводе — один put только
метаданных и ноль записей файлов. Первоначальный замер от input до следующего кадра:
максимум около 358 мс, 95-й перцентиль около 143 мс; после первого исправления —
46/41 мс, в повторном замере итоговой версии — 30/28 мс. Это сравнительный замер
локальной dev-сборки, не гарантия задержки на любом устройстве. Прошли 50 frontend-
тестов, ESLint и production build с TypeScript.

Chrome проверяет настоящий upgrade браузерного хранилища с v1 и File; перезагрузку
до истечения 450 мс; восстановление текста и всех вложений; Esc отмены picker;
HTTP 503 публикации с сохранением черновика; закрытие/повторное открытие; успешную
публикацию с побайтовым совпадением исходных файлов; очистку после публикации.
Все записи этих проверок выполняются только в отдельной QA-базе, не на production.

Frontend-тесты проверяют отдельное хранение файлов, отсутствие повторных Blob-записей,
очистку удалённых вложений, старые черновики, quota fallback и более новый текстовый
checkpoint. Схема серверной SQLite не меняется; выпуск использует обычный CI/CD.
