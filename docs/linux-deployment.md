## Выбранная схема

```text
Интернет → Caddy :443 → Next.js 127.0.0.1:3000
                              ↓ /api/v1/*
                       FastAPI 127.0.0.1:8000
                              ↓
                       /var/lib/nen/pact.db
```

Для первого размещения сохраняем одну VM и SQLite. Next.js и FastAPI работают как отдельные непривилегированные процессы. На Linux с systemd используются две службы с автозапуском и перезапуском при сбое. Caddy принимает внешний HTTP/HTTPS и передаёт запросы Next.js. API и Node-порты остаются на loopback. Через существующий Next.js rewrite браузер использует один домен и cookie.

Первоначальная схема предполагала HTTPS на 443. После обнаружения Xray для текущей VM выбираем 8443; HTTP 80 используется для ACME HTTP-01 и перенаправления на HTTPS с портом 8443. TLS-ALPN challenge отключён, так как проверка CA всегда шла бы на занятый Xray порт 443. Caddy работает по HTTP/1.1 и HTTP/2, без необходимости UDP-порта для HTTP/3.

Домен с A/AAAA-записью на VM и доступными снаружи портами 80/443 позволяет Caddy настроить публичный HTTPS. При отсутствии домена способ первичной проверки выбирается отдельно; включать Secure-cookie нужно вместе с рабочим HTTPS.

## Уточнение для Ubuntu 22.04: подготовка окружения

Эта запись уточняет первоначальный общий ориентир Python 3.12/3.13: для подтверждённой Ubuntu 22.04 используем штатный Python 3.10 в отдельном venv. Не заменяем `/usr/bin/python3`. Установка зависимостей и запуск API на этой версии ещё должны быть проверены на VM.

При 2 ГиБ RAM сборка Next.js может потребовать больше памяти; перед первой сборкой добавляем 4 ГиБ swap. Это запас памяти на диске, а не гарантия производительности сайта. Node устанавливаем из официального Linux x64 архива в версионный каталог `/opt`, с проверкой SHA-256 по опубликованному HTTPS-манифесту. Это проверка целостности загрузки, не отдельная проверка подписи релиза. Общесистемные ссылки в `/usr/local/bin` позволяют будущему пользователю службы пользоваться Node без nvm в `/root` и без загрузки shell-профиля. Обновления Node выполняются отдельно; APT эту установку не обновляет.

Все блоки этого раздела — Bash в **консоли Ubuntu от root**, последовательно. При ошибке следующий блок не выполнять. На этапе подготовки сетевые порты и firewall не меняются.

Пакеты:

```bash
apt update
apt install -y ca-certificates curl xz-utils python3-venv python3-pip build-essential sqlite3
```

Swap: блок создаёт отдельный файл и отказывается перезаписывать существующий. `dd` выделяет реальные блоки файла. Если `/swapfile-nen` уже существует, сначала нужно проверить его состояние; не удалять и не форматировать повторно вслепую.

```bash
(
  set -eu
  umask 077
  test ! -e /swapfile-nen
  dd if=/dev/zero of=/swapfile-nen bs=1M count=4096 status=progress conv=excl
  chmod 600 /swapfile-nen
  mkswap /swapfile-nen
  swapon /swapfile-nen
  if ! grep -qE '^[[:space:]]*/swapfile-nen[[:space:]]' /etc/fstab; then
    printf '\n/swapfile-nen none swap sw 0 0\n' >> /etc/fstab
  fi
)
```

Node.js: версия 24.22.0 проверена по официальной странице загрузки 19 октября 2026 года. Проверяется только строка нужного архива из манифеста. Временный каталог уникален; при неудачной загрузке или несовпадении контрольной суммы установка прекращается до распаковки.

```bash
(
  set -eu
  nen_node_version=v24.22.0
  nen_node_archive="node-${nen_node_version}-linux-x64.tar.xz"
  nen_node_tmp="$(mktemp -d)"
  cd "$nen_node_tmp"
  curl -fSLO "https://nodejs.org/dist/${nen_node_version}/${nen_node_archive}"
  curl -fSLO "https://nodejs.org/dist/${nen_node_version}/SHASUMS256.txt"
  grep "  ${nen_node_archive}$" SHASUMS256.txt > nen-node.sha256
  sha256sum -c nen-node.sha256
  install -d /opt
  tar -xJf "$nen_node_archive" -C /opt --no-same-owner
  for nen_command in node npm npx; do
    ln -sfn "/opt/node-${nen_node_version}-linux-x64/bin/${nen_command}" "/usr/local/bin/${nen_command}"
  done
)
```

## Перенос исходников и сборка

Для этой установки готовим единый архив всего приложения, поскольку Git-репозиторий пока находится только в `web`. Скрипт `scripts/package-deployment.py` создаёт `.deploy/nen-source.tar.gz` и `.deploy/nen-source.sha256` по списку нужных каталогов и файлов. Локальные `.env`, базы SQLite, `.git`, Windows venv, node_modules, .next и Python-кэши в архив не входят. Исходные изображения сохраняются. При `--backup-database` создаётся отдельная согласованная SQLite-копия в `.local-backups`, проверенная через quick_check и foreign_key_check. Она не попадает в архив и не переносится автоматически.

Локально подготовлен и проверен архив: 121 файл, около 5.2 МиБ. Проверены необходимые API/frontend-файлы, совпадение зависимостей package.json с lock-файлом, отсутствие БД, рабочих env и Windows-зависимостей, безопасные относительные пути архива и SHA-256. Отдельная копия данных: `.local-backups/before-vm-deploy-20261019T094043038558Z.sqlite3`. На VM эта проверка не заменяет установку зависимостей, сборку и запуск.

При первой проверке на Ubuntu обнаружен CRLF в `nen-source.sha256`: GNU sha256sum воспринимает `\r` как часть имени архива. Предыдущая локальная проверка использовала split и пропустила этот дефект формата. Генератор исправлен на запись ASCII-байтов с LF, независимо от ОС. Для уже переданного файла выполнить `sed -i 's/\r$//' /root/nen-source.sha256` и повторить проверку. Сам архив для этого пересоздавать и повторно передавать не требуется; его содержимое и контрольная сумма не меняются. Передача файлов до этого места состоялась, распаковка была остановлена проверкой и пока не подтверждена.

## Первый запуск служб: пустая база и SSH-туннель

Решение пользователя — начать с пустой БД. Подготовленный `scripts/setup-vm-services.sh` предназначен только для первой установки. Он проверяет пользователя `nen`, готовую `.next/BUILD_ID`, исполняемые Node/Python и свободные loopback-порты 3000/8000. Если постоянная БД или конфигурация служб уже существуют, он прекращает работу до их изменения. Данные и старые конфигурации не удаляются. Скрипт хранится с LF; пересоздавать уже переданный архив исходников ради него не требуется.

При первом запуске создаются:

- `/etc/nen/api.env`, root:nen, 0640: абсолютный путь к БД, debug=false и cookie_secure=false для локального HTTP через SSH.
- `/var/lib/nen/pact.db`: пустая схема API, созданная импортом `app.main` от пользователя `nen`, без демонстрационных записей.
- `nen-api.service`: один worker Uvicorn на `127.0.0.1:8000`. Один процесс сохраняет смысл текущих внутрипроцессных блокировок SQLite; масштабирование потребует отдельного решения.
- `nen-web.service`: production Next.js на `127.0.0.1:3000`. Служба запускает Node напрямую, без dev-режима, npm-оболочки и PM2.

Обе службы работают от `nen`, запускаются после перезагрузки и перезапускаются при ошибке. В service-файлах защищена запись в файловую систему: API пишет в `/var/lib/nen`, Next.js — в `.next` для кэша. У API доверенные forwarded-заголовки принимаются только от loopback-прокси. Перед стартом на VM выполняется `systemd-analyze verify`; после старта — health напрямую, health через rewrite Next.js и загрузка главной страницы.

На Windows, PowerShell:

```powershell
scp D:\projects\nen\scripts\setup-vm-services.sh root@144.31.189.98:/root/
```

На Ubuntu, root:

```bash
bash /root/setup-vm-services.sh
```

Ожидаются два JSON-ответа `{"status":"ok"}`, успешная HTTP-проверка главной и `active (running)` у обеих служб. Это ожидаемый результат; реальное выполнение на VM подтверждается отдельно. Локально проверяются Bash-синтаксис и LF; локальная Windows-сессия не является systemd-средой.

Если установка остановилась после создания конфигурации, не удалять БД ради повторного запуска: сначала читать указанную ошибку и журналы, затем продолжать с нужного этапа. Диагностика на VM:

```bash
systemctl --no-pager --full status nen-api.service nen-web.service
journalctl -u nen-api.service -u nen-web.service -n 80 --no-pager
```

Для браузера открыть **отдельное окно PowerShell на Windows** и оставить его работающим:

```powershell
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:3333:127.0.0.1:3000 root@144.31.189.98
```

Сайт доступен на `http://127.0.0.1:3333`. Локальный порт 3333 выбран отдельно от порта 3000 исходного Windows dev-сервера. Трафик между Windows и VM шифрует SSH; приложение слушает только loopback VM. Для этой проверки firewall не меняется. Это ещё не публичная публикация. Перед внешним HTTPS-доступом настроить Caddy и `PACT_COOKIE_SECURE=true`, проверить вход и повторный старт служб. Поле Secure нельзя включать для текущего HTTP-просмотра.

Уточнение к SSH-проверке: команду запускать в локальном PowerShell Windows, а не в `root@temich` на VM. После ввода пароля оставить окно открытым и открыть URL в браузере своего компьютера. Отсутствие shell-приглашения с `-N` ожидаемо. Туннель нужен для предварительной проверки до публичного прокси; после настройки Caddy для обычного посещения сайта он не понадобится. Если браузер всё же не открывает страницу, во втором локальном PowerShell проверить `curl.exe -v http://127.0.0.1:3333/api/v1/health`; это помогает отличить ожидание SSH от ошибки перенаправления.

## Подготовка внешнего доступа после успешного запуска

Перед установкой Caddy проверяем существующие TCP/UDP-слушатели 80/443 и TCP admin-порт 2019. Существующие приложения и правила SSH не останавливаем и не заменяем без разбора фактической конфигурации.

```bash
ss -lntup '( sport = :80 or sport = :443 or sport = :2019 )'
if command -v ufw >/dev/null; then
  ufw status verbose
fi
```

Пока результат этих команд не получен, Caddy и firewall не изменены. Проверка ufw сама по себе не описывает внешний firewall хостинга или все возможные правила nftables/iptables; достижимость проверяется отдельно после настройки.

Публичный DNS-домен удобен, но не является обязательным условием HTTPS: Let's Encrypt с января 2026 года выдаёт IPv4/IPv6-сертификаты через ACME-профиль `shortlived` (160 часов). У Caddy стандартный режим для IP использует внутренний CA, поэтому для публично доверенного IP-сертификата требуется явно указать ACME issuer и профиль. Проверены официальный TLS-синтаксис `profile shortlived`, параметр `default_sni` для клиентов без SNI и актуальный релиз Caddy 2.11.7; связанная ошибка выпуска IP-сертификатов рассмотрена в issue #7399. Конкретная конфигурация ещё не применена и будет выбрана после ответа о домене и проверки портов. Короткий срок сертификата требует постоянно работающего автоматического продления и доступных ACME-проверок. Покупка домена не требуется для продолжения подготовки.

## Установка Caddy рядом с Xray

Скрипт `scripts/setup-vm-caddy.sh` — первая установка для этой VM. Перед изменениями проверяет готовность API, ожидаемый путь БД, cookie_secure=false и отсутствие прежней установки/конфигурации Caddy. Затем проверяет свободные TCP 80/8443/2019; при конфликте завершает работу до установки пакетов. Команды управления Xray отсутствуют. База не создаётся заново и не переносится.

Порядок:

1. Официальный stable-репозиторий Caddy, пакет не старее 2.11.7. `NEEDRESTART_MODE=l` ограничивает needrestart выводом списка; другие службы автоматически не перезапускаются через needrestart.
2. Резервная копия начального Caddyfile и проверка сгенерированного конфига через `caddy validate`.
3. Caddy на 8443 с `default_sni` равным публичному IP, явным Let's Encrypt ACME issuer, профилем `shortlived` и HTTP-01 на 80. До готовности сертификата возвращает служебный 503. Тело запроса ограничено 60 МиБ, что оставляет место для 50 МиБ вложений и multipart-обвязки.
4. Если ufw установлен и активен, добавляются разрешения TCP 80/8443; сам firewall не включается и SSH-правила не переписываются. Правила панели хостинга должны пропускать TCP 80 для CA и TCP 8443 для посетителей. Продление IP-сертификата требует сохранять доступность 80.
5. Проверка доверия сертификату и соответствия IP через обычный curl, без `-k`, с подключением к loopback на 8443. Ожидание примерно до трёх минут. Это проверяет серверный TLS; внешнюю доступность 8443 ещё нужно проверить с компьютера пользователя.
6. Только после успешной TLS-проверки сохраняется копия `/etc/nen/api.env`, включается `PACT_COOKIE_SECURE=true`, перезапускается API, а Caddy переключается с 503 на Next.js. Выполняются HTTPS health, загрузка главной и проверка Secure/HttpOnly в ответе logout без cookie, то есть без удаления чужой сессии.

Перенос скрипта из Windows PowerShell:

```powershell
scp D:\projects\nen\scripts\setup-vm-caddy.sh root@144.31.189.98:/root/
```

Запуск в root-консоли Ubuntu:

```bash
bash /root/setup-vm-caddy.sh
```

После сообщения `Server checks passed` открыть `https://144.31.189.98:8443/` с Windows, войти в аккаунт и проверить создание пакта/отметку и загрузку файла. На новом адресе потребуется войти заново, так как cookie привязана к другому хосту; существующие аккаунты и данные сохраняются. Для постоянного адреса туннель больше не нужен. Браузерная проверка и доступность снаружи подтверждаются отдельно.

Если установка прервана, прислать вывод и `journalctl -u caddy -u nen-api -n 80 --no-pager`. Это скрипт первой установки: повторный запуск после частичной установки откажется перезаписывать существующий Caddy. Дальнейшие действия выполняются по фактической ошибке, без удаления БД или сертификатов. При недоступном ACME API остаётся со старой настройкой cookie, а Caddy — со служебной страницей; после включения Secure-cookie для просмотра следует использовать HTTPS.

Локальная проверка: Bash-синтаксис, LF без BOM и генерация финального Caddyfile через `--print-config`. Загрузка локального Caddy для дополнительной CLI-проверки оказалась недоступна из-за ограничения сети среды. Сам Caddy валидирует оба конфига на VM до применения. Получение сертификата, выполнение apt/systemd и внешняя доступность локально не заявляются проверенными.

## Перенос с 8443 на 443 после освобождения порта

Рабочая конфигурация на VM: `/etc/caddy/Caddyfile`. Перенос применяется только после проверки, что предыдущий сервис больше не слушает TCP 443. Прежний Xray пользователь останавливает/переносит самостоятельно; имя systemd-службы нельзя выводить только из имени процесса.

```bash
ss -lntp '( sport = :443 )'
```

Сохранить отдельную копию перед правкой:

```bash
cp -p /etc/caddy/Caddyfile "/etc/caddy/Caddyfile.before-443-$(date -u +%Y%m%dT%H%M%SZ)"
```

В Caddyfile меняются **оба** места: `https_port 8443` → `https_port 443` и адрес блока `https://144.31.189.98:8443 {` → `https://144.31.189.98 {`. Отдельный параметр https_port относится к серверному слушателю, а адрес блока задаёт адрес сайта, поэтому одной замены глобального порта недостаточно. Значения backend 3000/8000 сохраняются. В конфигурации остаётся существующий публичный ACME issuer с профилем shortlived, cookie_secure=true и HTTP-01 на порту 80.

Для текущего сгенерированного конфига обе замены можно выполнить без редактора:

```bash
sed -i \
  -e 's/https_port[[:space:]]\+8443/https_port 443/' \
  -e 's#https://144\.31\.189\.98:8443#https://144.31.189.98#' \
  /etc/caddy/Caddyfile
```

После правки проверка, запуск backend/frontend при необходимости и применение Caddy:

```bash
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
systemctl start nen-api.service nen-web.service
systemctl reload-or-restart caddy.service
curl -fsS --noproxy '*' --connect-timeout 5 --max-time 15 \
  --connect-to 144.31.189.98:443:127.0.0.1:443 \
  https://144.31.189.98/api/v1/health
```

При ошибке validate не применять reload/restart. Если Caddy уже работает, reload-or-restart использует reload, а остановленный сервис запускается. Новый публичный адрес — `https://144.31.189.98/`, без указания порта. На сетевых экранах нужны TCP 443 и 80; 80 сохраняется для действующей схемы автоматического продления IP-сертификата. Старое правило 8443 можно убрать после проверки нового адреса. Первоначальный установщик `setup-vm-caddy.sh` остаётся историей первой установки на 8443; повторно запускать его для переноса не требуется.

## Настройки текущего проекта

API:

```dotenv
DATABASE_URL=sqlite:////var/lib/nen/pact.db
PACT_DEBUG=false
PACT_COOKIE_SECURE=true
```

`PACT_COOKIE_SECURE=true` — для публичного запуска по HTTPS. API сейчас читает окружение процесса через `os.getenv`; сам по себе файл `.env` не загружается. В systemd эти значения передаются через `EnvironmentFile`.

Frontend:

```dotenv
NEN_API_ORIGIN=http://127.0.0.1:8000
```

Значение должно быть доступно при сборке. `NEXT_PUBLIC_API_URL` оставляем незаданным: браузер использует `/api/v1`, а не адрес локальной машины посетителя.

Проверочные команды после подготовки окружения:

```bash
curl -fsS http://127.0.0.1:8000/api/v1/health
curl -fsS http://127.0.0.1:3000/api/v1/health
```

После настройки HTTPS проверяются тот же health через домен и реальные cookie/файлы. При выборе внешнего reverse proxy необходимо сохранить лимит загрузки поста: до 50 МиБ вложений плюс служебные данные. В Next.js уже предусмотрен буфер 60 МиБ.
