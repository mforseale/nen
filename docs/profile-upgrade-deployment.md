# Выпуск профилей и автоматических стриков на VM

Решение от 20 октября 2026. По запросу пользователя готовим публикацию накопленных
изменений. Это заменяет временное ограничение «не выполнять push в main» из
[responsive-social-and-streaks.md](responsive-social-and-streaks.md).
Обычный CD по-прежнему не меняет схему базы.

## Почему нужен отдельный переход

Рабочая версия ожидает `20261019_0001`, новая — `20261019_0002`. Установка только
кода или только миграции не образует совместимую пару. Пять новых таблиц добавляются
без удаления прежних строк/файлов. Предыдущая копия кода от `0001` не запускается с
базой `0002`; обычный rollback установщика это проверяет и отказывает.

Для этого выпуска добавлена root-команда `deploy_vm.py install-profile-upgrade`.
Она принимает исключительно переход `0001 → 0002` и SHA исходного commit.
Ограниченный SSH gate не умеет вызывать эту команду: авторизованный оператор
запускает её через отдельную transient-службу systemd.

## Порядок выпуска

1. На время выпуска установить repository variable `NEN_CD_ENABLED=false`, чтобы
   workflow не пытался установить пакет раньше согласованного перехода.
2. Отправить проверенные исходники в `main`, дождаться зелёного **CI**, включая
   запуск готового Linux-пакета и существующий SSH/systemd fixture.
3. Скачать artifact `nen-runtime-<commit>`. Он содержит `nen-runtime.tar.gz`,
   SHA-256, `nen-source-commit.txt`, установщик и `start-profile-upgrade.sh`.
   Передать содержимое в новый каталог под `/root/` на VM, распаковывая ZIP до
   запуска shell-команды. Базу и рабочие env из локального проекта не отправляем.
4. Выполнить `bash /root/<каталог>/start-profile-upgrade.sh` под root. Наблюдать:
   `journalctl -fu nen-profile-upgrade.service`. Работа продолжается при обрыве SSH.
5. После строки `Deployment verified` проверить HTTPS health/главную, вход,
   свои посты и профиль. Затем вернуть `NEN_CD_ENABLED=true` для следующих
   обновлений той же схемы.

## Что делает установщик

- Берёт общий lock деплоя, проверяет существующие службы/пути/БД/Node/Python и SHA.
- Подготавливает зависимости без сети, пока старый сайт работает.
- Репетирует миграцию на отдельной восстановленной копии; сравнивает содержимое
  всех прежних таблиц, включая BLOB. Рабочая база в репетиции открывается для чтения.
- Останавливает Caddy, затем web/API: внешние записи до подтверждения новой версии
  закрыты. Конфигурация Caddy и сертификаты остаются на месте.
- Создаёт один постоянный проверенный снимок в `/var/backups/nen`, переключает код,
  мигрирует БД, ещё раз сравнивает прежние строки/файлы, запускает API/web и health.
- После успешных проверок сохраняет одну `/srv/nen-previous` с прежними зависимостями
  и ссылкой на совместимый снимок в `previous.json`, запускает Caddy.

Репетиционные снимки и внутренний снимок миграционной транзакции находятся во
временной папке подготовки и удаляются после успешного завершения/восстановления.
Дополнительно остаётся один полный снимок именно этого перехода; ежедневная
политика хранения не меняется. Новых каталогов релизов не накапливаем.

## Восстановление при ошибке

До повторного открытия Caddy при неудачном запуске новые службы останавливаются,
SQLite backup API восстанавливает базу в существующий файл с учётом WAL, затем
возвращаются прежний код/зависимости и проверяется старый сайт. Это восстановление
разрешено только внутри закрытого перехода: пользовательские записи новой версии
через публичный адрес ещё не принимались.

Если не удалось остановить службы или восстановить базу, Caddy остаётся выключен,
обе версии и `/srv/nen-deploy-state.json` сохраняются. Журнал содержит путь к
снимку. Продолжение требует диагностики; нельзя удалять marker и просто запускать
старый код с новой схемой. После успешного публичного выпуска автоматический
возврат старого снимка не предлагается: он потерял бы новые записи.

## Проверки

Временные SQLite и каталоги проверяют весь координатор: обычный CD отказывает
до остановки служб; успешный переход сохраняет строки/BLOB; ошибка health
возвращает совместимые код и базу до открытия публичного доступа; ошибка самого
восстановления удерживает шлюз закрытым и сохраняет marker/снимок/обе версии.
Отдельные тесты проверяют WAL, повреждённый snapshot и неверную ревизию источника.
Системные команды/пользователи/фиксированные пути в этих тестах заменены, рабочие
данные не затрагиваются. Существующая Linux-проверка SSH/systemd остаётся в CI.

На момент подготовки этого документа новая версия на production ещё не установлена.
