Это уточняет первоначальный установщик ниже; рабочая схема с одной предыдущей копией сохранена.

## Что хранится на VM

| Путь | Назначение |
|---|---|
| `/srv/nen/api`, `/srv/nen/web` | Работающее приложение |
| `/srv/nen-previous` | Одна предыдущая версия API, frontend и их зависимостей; настройки перехода между `next start` и standalone |
| `/srv/.nen-deploy-*` | Временная подготовка обновления; после нормального завершения удаляется |
| `/srv/nen-deploy-state.json` | Только во время переключения; при аварии сохраняет путь к незавершённой операции |
| `/etc/systemd/system/nen-web.service.d/nen-standalone.conf` | Запуск нового frontend через `node /srv/nen/web/server.js` на loopback 3000 |
| `/run/nen-deploy/lock` | Запрет одновременных установок и откатов |

SQLite `/var/lib/nen/pact.db`, `/etc/nen/api.env`, Caddy, сертификаты и ежедневный backup timer остаются вне обновляемого приложения. Установщик не перезаписывает БД и не выполняет SQL-миграции. Он разрешает только сборку, совместимую с уже зарегистрированной схемой, проверяя её через `app.db_admin check` до остановки служб. Будущая миграция схемы требует отдельного проверенного шага; новая схема может запретить откат к старому коду.

Замеры пользователя: БД 2,5 МБ, `/var/backups/nen` 13 МБ, свободно 18 ГБ. **Оставляем уже установленное хранение 14 daily**; обсуждавшееся сокращение до 3/2 не принято и не реализовано. Копии перед миграциями и ручные копии не удаляются этой работой.

## Сборка и проверки

CI сначала проверяет API и сценарии восстановления. Затем проверяет frontend, собирает Next.js `output: standalone` на Ubuntu 22.04 x64 / Node 24 и скачивает Python 3.10 wheels всех API-зависимостей. Сборка frontend на VM больше не нужна. Native-зависимости создаются на Linux, Windows-сборки не используются.

`scripts/runtime_bundle.py` формирует `nen-runtime.tar.gz` и LF-файл `nen-runtime.sha256`. В архиве только API-код, Alembic, requirements, wheels, минимальный frontend runtime, `public`, `.next/static` и `runtime.json` с SHA исходников. Venv, БД и рабочие `.env` не включаются. Зафиксированная папка wheels делает установку зависимостей из этого архива автономной, хотя исходный requirements пока фиксирует только прямые зависимости.

`scripts/smoke_runtime.py` распаковывает именно готовый архив, устанавливает API без сети в отдельный venv, создаёт временную БД миграциями и запускает оба сервера. Проверяет health API/прокси, страницы, JS/CSS, фон, native sharp image optimizer, регистрацию и cookie-сессию. Тестовые процессы и БД удаляются; production недоступен из CI.

Только успешный `main` публикует Actions artifact `nen-runtime-<полный SHA>`, содержащий архив, checksum, два установочных Python-файла и этот документ. Срок хранения в GitHub — 7 дней; на VM каталоги релизов не накапливаются. PR проходит такие же проверки, но не публикует установочный artifact.

## Первая установка готового пакета

Текущий этап: сборка и установка по команде оператора. Автоматическая доставка по SSH из Actions ещё не подключена; это следующий этап. На VM заранее подготовлены пользователь `nen`, работающие systemd-службы, Node 24, Python 3.10 с `venv` и зарегистрированная Alembic baseline.

1. Открыть успешный запуск **GitHub → Actions → CI** для нужного commit и скачать artifact `nen-runtime-<SHA>`. Распаковать ZIP в отдельную локальную папку. Для скачивания через интерфейс требуется вход в GitHub; публичность репозитория не делает API скачивания artifacts анонимным.
2. Передать файлы из этой папки на VM в `/root/nen-update/` через SCP/SFTP. Не смешивать их с прежним `nen-source.tar.gz`: это другой формат, готовый runtime.
3. На VM от root:

```bash
(
  set -eu
  cd /root/nen-update
  sha256sum -c nen-runtime.sha256
  runtime_sha="$(cut -d ' ' -f 1 nen-runtime.sha256)"
  /usr/bin/python3 deploy_vm.py install nen-runtime.tar.gz --sha256 "$runtime_sha"
)
```

Установщик проверяет реальную конфигурацию запущенного API, версии runtimes, checksum и структуру архива. Ссылки, выходы из каталога, специальные файлы и повторные пути архива запрещены. До остановки сайта готовит тестовый venv и проверяет зависимости/совместимость БД. Затем останавливает две app-службы, переносит старые каталоги во временную копию, ставит новые, создаёт venv **по конечному пути** и устанавливает зависимости из wheels без сети. Venv не переносится с CI или временного пути; старый venv при откате возвращается на свой исходный путь.

После запуска проверяются API, frontend proxy и главная. Только успешная проверка заменяет `/srv/nen-previous`. При обычной ошибке установки или запуска возвращаются старые каталоги, зависимости и прежний override web-службы; более старая предыдущая копия также сохраняется. Остальные каталоги `/srv/nen` не переносятся и не удаляются. Короткий простой включает автономную установку API-зависимостей и проверки готовности. Frontend при этом не собирается.

## Откат

Тем же установщиком из доверенного пакета:

```bash
/usr/bin/python3 /root/nen-update/deploy_vm.py rollback
```

Проверяется совпадение ревизии живой БД с записанной при сохранении предыдущего приложения. Меняются код, зависимости и настройка запуска frontend; живая БД не восстанавливается из старого снимка. После успешного отката бывшая рабочая версия становится единственной предыдущей копией, поэтому можно вернуться обратно. Поддержан и откат первой установки к исходному frontend с `next start`.

`SIGTERM`, `SIGHUP` и Ctrl+C проходят обычное восстановление. `SIGKILL`, выключение питания или ошибка самого восстановления могут оставить marker и временную папку. Новая установка откажется продолжать. Сначала посмотреть `/srv/nen-deploy-state.json`, содержимое указанного `work/old` и рабочие каталоги, `systemctl status`/`journalctl`. Не удалять marker или временную копию до восстановления согласованного состояния. Это ограничение переключения двух каталогов без release-symlink; прежние настройки systemd и файлы остаются в `old/config`.

Подтверждённые результаты Linux CI и первой установки на настоящей VM зафиксированы выше. Автоматическая SSH-доставка пока не подключена.
